# PJR-QHKA 別リポジトリ構成（Detached Unit）のドキュメント化

## 1. 概要

SpecDojo の成果物をプロダクトと同じリポジトリに置かず、別リポジトリ（`app1-specdojo/`）で
運用する構成を `docs-structure-guide.md` へ追記する。採用条件、ディレクトリレイアウト、
result への app commit hash 記録によるトレーサビリティ方式を規定する。

現在のガイドは同一リポジトリ構成だけを前提としており、別リポジトリ構成の記述がない。

## 2. 方案の評価

### 2.1. 想定する構成

プロダクトと SpecDojo をリポジトリで分け、SpecDojo 側から開発を管理する。

```text
app1/                 プロダクト（別リポジトリ）
app1-specdojo/        SpecDojo（別リポジトリ）。npm i -D specdojo で CLI を入れる
app1-worktrees/       worktree の置き場
```

動機はプロダクトリポジトリの見通しを良くすることである。SpecDojo は1つの登録簿項目につき
`start` / `wait` / `review` / `close` の遷移 commit と統合 commit を生み、成果物の更新も加わる。
プロダクトの変更履歴を追う目的からは雑音になる。物量も大きく、本リポジトリでは kata だけで
301文書ある。

### 2.2. 成立を支える実装上の事実

| 要素             | 実装                                                     |
| ---------------- | -------------------------------------------------------- |
| ルート決定       | `.specdojo/` の位置から上方探索する。git には依存しない  |
| パス解決         | `specdojo.config.json` が相対パスで宣言する              |
| リポジトリ外拒否 | `grade` と `register` にはあるが、exec の実行系にはない  |
| 親検証           | `cwd` を引数で受ける（`invoke(definition, cwd)`）        |
| 親検証の内容     | `npm run test:unit` など。実行場所が変われば対象も変わる |

exec の実行系にリポジトリ外を拒否するガードはなく、親検証も `cwd` を受け取る設計である。
構成として原理的に不可能ではない。

### 2.3. 現状で未対応の点

一方、次は単一リポジトリを前提としており、多リポジトリでは追加の対応が要る。

| 論点              | 現状                                                                    |
| ----------------- | ----------------------------------------------------------------------- |
| 編集対象の解決    | job の `paths` と task の `targets` は SpecDojo ルート相対              |
| worktree の隔離   | SpecDojo リポジトリの worktree を作る。プロダクト側は隔離外             |
| commit のスコープ | SpecDojo リポジトリに対して計算する。プロダクト側の commit 主体が未定義 |
| 親検証の実行場所  | SpecDojo ルートで実行する。プロダクトへ向ける設定がない                 |

worktree の置き場を分けても、隔離されるのは SpecDojo 側だけである。agent がプロダクトを
編集すると、その変更は隔離の外に出る。並行実行と失敗時のロールバックが効かない。

### 2.4. product docs の配置

プロダクトの docs をどちらへ置くかは、SpecDojo が管理するかどうかで決まる。本リポジトリの
実態は次のとおりである。

| 指標                              | 実測      |
| --------------------------------- | --------- |
| 成果物カタログ（`dct-*.yaml`）    | 28 件     |
| うち `docs/ja/product` を指すもの | **21 件** |

カタログは `base_path: /docs/ja/product/...` の形で product docs を成果物として宣言する。
`deliverable scaffold` が雛形を生成し、exec が編集し、grade が評価する対象である。

つまり product docs は「プロダクトの付属文書」ではなく、**SpecDojo が管理する成果物そのもの**で
ある。`app1/docs/ja/product` へ置くと、SpecDojo の中核である catalog / exec / grade がリポジトリを
またぐことになり、最も更新頻度の高い文書がすべて多リポジトリ対応を必要とする。

| 配置                            | 評価                                            |
| ------------------------------- | ----------------------------------------------- |
| `app1/docs/ja/product`          | 分離の利点が小さく、対応コストが大きい          |
| `app1-specdojo/docs/ja/product` | catalog / exec / grade が単一リポジトリで閉じる |

`app1-specdojo/` 側を推す。プロダクトリポジトリの見通しを良くする目的にも合致する。文書を
プロダクト側へ残すと、見通しの改善そのものが薄まる。

ただしトレードオフがある。プロダクトの実装と設計文書が別リポジトリになるため、実装変更と
文書更新が1つの commit にまとまらない。README や API リファレンスなど、プロダクト利用者が
コードと同じ場所で読むべき文書は `app1/` に残す判断があり得る。SpecDojo が成果物として管理する
文書と、プロダクトに付属する文書を分けて考える。

### 2.5. 二重 worktree による並行実行

docs とソースの両方を1つの登録簿項目で扱う場合、両リポジトリの worktree を `app1-worktrees/`
配下へ作り、`app1-specdojo/` の specdojo コマンドが両方を管理する構成が考えられる。

```text
app1-worktrees/
  <task-id>/
    docs/     app1-specdojo の worktree
    src/      app1 の worktree
```

#### 2.5.1. 実装が許す部分

`ensureExecWorktree` は `repoRoot` を引数で受け取る。特定のリポジトリに固定されていないため、
同じ関数で別リポジトリの worktree を作れる。

```text
ensureExecWorktree({ repoRoot, worktreeBase, taskId, ... })
```

`worktreeBase` はリポジトリ外であることを要求する。`app1-worktrees/` は両リポジトリの外にあり、
この制約を満たす。branch 名は task ID から決まるため、両リポジトリで同じ名前を使える。

#### 2.5.2. 単一リポジトリを前提とする部分

統合処理は `repoRoot` と `worktree.path` の2つだけを文脈として持ち、1組の対応関係を前提とする。

| 処理           | 現状                                                          |
| -------------- | ------------------------------------------------------------- |
| commit 対象    | `repoRoot` に対して算出する                                   |
| merge 先       | `repoRoot` で checkout 中のブランチ                           |
| 比較基準       | `merge-base HEAD <rootHead>` を `repoRoot` と worktree で取る |
| pipeline-state | `task_id` と `run_id` で1つ。リポジトリの区別を持たない       |

二重 worktree にすると、これらがすべて2組必要になる。

#### 2.5.3. 統合順序と部分状態

docs とソースの両方を扱う項目では、ソースを先に統合し、成功した場合だけ docs を統合する。
この順序により、起こり得る部分状態は1通りに定まる。

| 失敗箇所     | 結果               | 扱い                        |
| ------------ | ------------------ | --------------------------- |
| ソースの統合 | 両方とも未統合     | 清潔。項目全体を再実行する  |
| docs の統合  | ソースのみ統合済み | docs の統合だけを再試行する |

任意の部分状態が生じるわけではないため、分散トランザクションのような一般的な回復手順は要らない。
回復に必要な仕組みは既にある。

- 統合段のみの再試行は `exec run --resume` が担う。executor と reporter が成功済みで統合だけが
  失敗した run を、agent を起動せず統合から再開する。
- 統合済みブランチの再 merge は `isExecBranchMergedIntoCurrent` が防ぐ。ソースを二重に統合しない。

ソースを先に統合する順序は、プロダクトの完全性を優先する点でも妥当である。SpecDojo 側の失敗が
プロダクトへ波及しない。

#### 2.5.4. 定義が必要な事項

部分状態そのものは扱えるが、次は運用上の定義を要する。

- **部分状態での item_status**。ソース統合済みで docs 未統合の項目は `waiting` とする。完了条件を
  満たしておらず、再開で docs の統合だけを行うためである。`review` にすると実質完了として扱う
  ことになり、未統合の docs が追跡から外れる。
- **打ち切ったときの後始末**。docs の統合が繰り返し失敗して項目を諦める場合、ソースは統合済みの
  まま残る。放置するか revert するかを決める必要がある。ただしこれは通常の merge 後の判断と同じ
  であり、二重 worktree に固有の問題ではない。
- **並行実行時の履歴順序**。複数項目を並行実行すると、A のソース統合、B のソース統合、A の docs
  統合という順序が起こり得る。各リポジトリ内では直列化されるため衝突しないが、A のソースと A の
  docs の間に B が入る状態は生じる。履歴を追うときの前提になる。

#### 2.5.5. 実装が必要な事項

順序化で解ける課題とは別に、次は実装を要する。

- **親検証の割り当て**。`test-unit` はソース側、`lint:md` と `validate:schema` は docs 側で実行する
  必要がある。現在の親検証は `cwd` を1つしか持たないため、検証 ID ごとに実行先を宣言する仕組みが
  要る。
- **agent の作業ディレクトリ**。agent は両方を見る必要がある。`app1-worktrees/<task-id>/` を cwd に
  すれば両方が相対パスで見えるが、`paths` と `targets` の解決基準が「リポジトリルート相対」から
  「タスク作業ディレクトリ相対」へ変わる。既存の単一リポジトリ実行と規則が分岐する。
- **失敗時の worktree 保持**。現在は失敗した worktree を残して調査に使う。二重化した場合に
  どちらをどの条件で残すかを定める。
- **統合処理の複製**。commit 対象の算出、merge 先の決定、pipeline-state の記録は `repoRoot` と
  worktree の1組を前提とする。2組を扱えるようにする。

#### 2.5.6. 評価

構成として成立する。`ensureExecWorktree` が `repoRoot` を引数化しており、統合順序を定めれば
部分状態も1通りに収まる。回復に必要な統合段の再試行と再 merge の防止は既に実装済みである。

残るのは実装量と、上記の運用定義である。設計上の障害は見当たらない。

段階を分ける余地はある。docs のみを扱う項目（実装を伴わない要件・設計・計画の更新）であれば
統合先が1つで済み、二重 worktree の実装を待たずに別リポジトリ構成を試せる。

本項目は設計の整理までとするため、実装は範囲に含めない。ガイドには構成案、統合順序、部分状態の
扱い、未実装の事項を記載し、採用可否の判断材料を残す。

### 2.6. 適用範囲の整理

| 構成                                | 評価                                           |
| ----------------------------------- | ---------------------------------------------- |
| 文書のみを扱う（自己完結）          | 現状の実装で成立する                           |
| プロダクト駆動（本方案）            | 設計上あり得るが、多リポジトリ対応の実装が要る |
| SpecDojo 自身の開発（本リポジトリ） | 成果物と実装が同じ変更で動くため同一リポジトリ |

本項目は設計の整理までとし、多リポジトリ対応の実装は範囲に含めない。ガイドには構成の紹介と
あわせて、未対応の点と適用条件を明記する。

- 残課題は二重 worktree の実装（親検証の割り当て、agent の作業ディレクトリ、失敗時の worktree
