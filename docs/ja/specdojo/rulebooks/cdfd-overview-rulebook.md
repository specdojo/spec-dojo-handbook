# 概念データフロー図（全体概要）作成ルール

Conceptual Data Flow Diagram Overview Documentation Rulebook

業務または運用の全体を、プロセス領域と領域間の情報・イベントの流れとして定義するためのルールです。対象範囲を合意し、各領域を領域別 CDFD へ重複・欠落なく引き渡せる粒度を定めます。

## 1. 全体方針

- 全体概要は、業務または運用を構成するプロセス領域、領域間の受け渡し、外部主体、人間の判断境界を合意する概念仕様とします。
- 一つのプロセス領域を一覧表の一行と Mermaid 図の一つの代表ノードで表し、領域内の手順、状態遷移、例外経路は領域別 CDFD へ委譲します。
- 領域数が多い場合は、業務の性質が近い領域をプロセスグループへまとめ、概念データフローの代表ノードをプロセスグループ単位にできます。プロセスグループにまとめても、一覧表・個別プロセス領域主要入出力・委譲境界では領域ごとの記述を維持します。
- 一覧表を領域定義と分割境界の正本、Mermaid 図を領域間フローの正本として併用し、領域 ID と用語を一致させます。
- 各領域には固有の業務目的、起点イベント、主要入力、主要出力、データストア、詳細化先、委譲境界を割り当てます。
- 対象者、利用場面、対象範囲、対象外を明示し、人間が担う承認や最終判断をシステムまたは AI Agent に置き換えません。

## 2. 位置づけと用語定義

| 用語             | 定義                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------ |
| 全体概要         | 複数のプロセス領域と相互の受け渡しを表す最上位の CDFD                                      |
| プロセス領域     | 固有の業務目的と成果を持ち、一つの領域別 CDFD へ詳細化できる責務のまとまり                 |
| プロセスグループ | 業務の性質が近い複数のプロセス領域をまとめた集合。概念データフローの代表ノード単位にできる |
| 領域代表ノード   | 全体概要で一つのプロセス領域またはプロセスグループを代表する角丸長方形の Mermaid ノード    |
| 起点イベント     | プロセス領域を開始させる、発生した時点を判定できる出来事                                   |
| 領域間フロー     | 外部主体、プロセス領域、データストアの間で受け渡される情報・イベント・必要に応じた現物     |
| データストア     | 領域が参照または更新する、台帳、文書、ファイル、データベースなどの論理的な正本または保管先 |
| 補助操作         | 一覧、検索、状態参照、検証、dry-run など、独立した業務成果を作らず他の領域を支援する操作   |
| 詳細化先         | 全体概要の一領域を引き継ぎ、領域内のプロセス、判断、例外を定義する領域別 CDFD              |
| 委譲境界         | 対象外として他のプロセス領域へ委ねる事項と、その委譲先の領域 ID                            |

全体概要は領域分割と領域間の受け渡しを定義し、領域別 CDFD は一領域の内部を詳細化します。両者で同じ領域 ID、起点イベント、主要入出力、データストアを引き継ぎます。

## 3. ファイル命名・ID規則

- ファイル名は `cdfd-overview.md`、ドキュメント ID は `<authority>:cdfd-overview` を基本とします。
- 配置は対象プロダクトの業務仕様配下にあるデータフローディレクトリを基本とし、プロジェクト固有の現状分析はプロジェクト文書配下へ配置できます。
- 領域 ID は文書内で一意な `P-01` 形式とし、一覧表、Mermaid 図、個別プロセス領域主要入出力、委譲境界で同じ値を使います。
- 領域 ID の採番順に業務上の意味を持たせず、名称変更後も同じ責務を表す限り維持します。
- 詳細化先は `cdfd-<domain>` 形式の ID またはファイル名 stem とし、一領域から一つの領域別 CDFD を識別できる名称にします。

## 6. 記述ガイド

### 6.1. 導入文

- 対象業務または運用が何を扱うかを一文で定義します。
- 詳細な効果、指標、実装方式は列挙しません。

### 6.2. 目的

- 全体概要を使用する対象者と、承認、領域別詳細化、設計入力、網羅性確認などの利用場面を結び付けて記述します。
- 「分かりやすくする」のような曖昧な表現ではなく、「〇〇が△△と□□の境界を承認する」のように利用結果を判定できる表現にします。

### 6.3. 適用範囲

- 対象業務、開始点、終了点、組織またはシステム境界を明示します。
- 補助操作、領域内の手順、実装エビデンス、別成果物が責任を持つ事項を対象外として区別します。
- 人間と AI Agent の責任分担の原則は、本文で再定義せず、対応するプロジェクト概要やプロジェクト方針文書への参照に留めます。
- 特定プロジェクトの実行計画・スケジュール上のフェーズ名は、全体概要では扱いません。読者が前提知識なしに読める語彙を使います。

### 6.4. プロセス領域

<!-- prettier-ignore -->
| 列 | 記載内容 | 判定基準 |
| --- | --- | --- |
| 領域 ID | `P-01` 形式の安定した識別子 | 一覧、図、個別プロセス領域主要入出力、委譲境界で同じ ID を使う |
| プロセス領域 | 業務目的が分かる短い名称 | コマンド名や実装部品名だけにしない |
| 業務目的 | 対象者に生じる成果または維持する状態 | 手順や機能の列挙にしない |
| 主な担当 | 主担当ロールまたは外部主体 | 個人名にしない |
| 起点イベント | 領域の開始を判定できる出来事 | 「必要に応じて」で終わらせない |
| 領域別 CDFD | 領域を詳細化する一意の ID または仮置き名 | 一領域を複数の詳細化先へ重複させない |

- 独立領域にするのは、固有の起点イベントと業務成果を持ち、他領域と区別できる入力、出力、またはデータストアがある場合です。補助操作は、独立した判断結果や更新成果を持たない限り領域にしません。
- 主要入力、主要出力、データストアは一覧表の列に含めず、「個別プロセス領域主要入出力」へ記載します。一覧表は領域を横断して比較する項目に絞ります。

- 見出しには、詳細を個別プロセス領域主要入出力（5章）へ委譲する概要図であることが分かるよう「（概要）」を付けます。

### 6.6. 個別プロセス領域主要入出力

- プロセスグループを設けた場合は、グループごとに見出しを立て、グループが扱う範囲を数行で要約します。
- 領域 ID ごとに、主要入力、主要出力、データストアを表で示します。業務目的、主な担当、起点イベントは「プロセス領域」（3章）と重複させて記載しません。
- プロセスグループが一領域だけで構成される場合も、同じ表構成を省略せず記載します。

### 6.7. 委譲境界

- 領域 ID ごとに、対象外として他のプロセス領域へ委ねる事項と、その委譲先の領域 ID を表で示します。
- 詳細化先（正本としての役割を持つ領域別 CDFD）は「プロセス領域」（3章）の領域別 CDFD 列を参照する前提とし、本章では再掲しません。
- 委譲先が複数のプロセスグループにまたがる場合も、グループ単位に分割せず、領域 ID 順の一つの表にまとめます。

### 6.8. 凡例（本プロダクト共通）

- 本プロダクトの領域別 CDFD が複数存在し、共通のノード形状・色・絵文字を使う場合に設けます。単一の CDFD しか存在しない、または各 CDFD が凡例を再掲しても負担にならない規模の場合は省略できます。
- `specdojo:cdfd-mermaid-rulebook` が定義する全ノード種別（プロセス／プロセスグループ、起点イベント、データストア、物理保管、外部主体、情報の流れ、物の流れ）について、本プロダクトが実際に採用する色・絵文字の割り当てをサンプル図と対応表で示します。本図自体が業務データフローを表すものではないため、他章のプロセス領域や領域間フローとは独立させます。
- 各 CDFD（本書自身の 4 章、および領域別 CDFD）の凡例は、この章の定義を再掲せず、本章への参照に留めます。

<!-- specdojo:finding id=F004 severity=minor rule=vp-arc-conciseness 「領域 ID・名称の一致」「一領域一代表ノード」「代表ノード7〜9件」の同一条件が全体方針、記述ガイド、完成判定、禁止事項で反復されているため、完成判定をチェックリストの正本として他節を参照へ寄せる必要がある。 -->

### 6.9. 完成判定

- 一覧表の各領域が、概念データフローの代表ノード（直接またはプロセスグループ経由）、個別プロセス領域主要入出力、委譲境界へ一度ずつ登場します。
- 各領域について、起点イベントと詳細化先は「プロセス領域」（3章）、主要入力・主要出力・データストアは「個別プロセス領域主要入出力」（5章）、委譲境界は「委譲境界」（6章）から識別できます。
- 図のエッジから、領域間または外部主体との受け渡し内容と方向を説明できます。
- 補助操作と領域内詳細が全体概要へ独立領域として混入せず、委譲先が明らかです。
- 代表ノードの数が目安（おおむね7〜9件）を超えていないか、超える場合はプロセスグループへ統合されているかを確認できます。
- 「凡例（本プロダクト共通）」を設けた場合、他の CDFD がそれを再掲せず参照していることを確認できます。

## 7. 禁止事項

| 禁止事項 | 理由 |
| -------- | ---- |

<!-- specdojo:finding id=F017 severity=minor rule=vp-ux-language-consistency 禁止事項の理由にある「詳細概要」は本文で定義されておらず、正式見出しの「個別プロセス領域主要入出力」を指すなら同じ名称へ統一する必要がある。 -->

| 一つの領域を複数の代表ノードへ分割する | 領域と代表ノードの対応が崩れ、一覧表・図・詳細概要の突き合わせができなくなるため |
| 業務の性質が異なる複数領域を、理由の説明なく一つの代表ノードへ統合する | 詳細化先の境界が不明瞭になり、重複・欠落の確認ができなくなるため |
| 全体概要に領域内の操作手順、状態遷移、例外分岐、物理テーブル・カラム、SQL、実装クラス、詳細 API、コマンドオプションを記載する | 領域別 CDFD の責務であり、全体概要の粒度を超えるため |
| 一覧、検索、状態参照、検証、dry-run などを、固有の業務成果がないまま独立領域にする | 補助操作を業務成果と誤認させるため |
| 一覧表、図、個別プロセス領域主要入出力、委譲境界で、同じ領域・イベント・入出力・データストアに異なる名称を使う | 読み手が同一対象と判断できなくなるため |
| ラベルのない情報・現物のエッジ、起点または到達先のないエッジ、対応する一覧行のない代表ノードを残す | 受け渡しの内容・方向・対応関係が読み取れなくなるため |
| 人間が責任を持つ主要判断、承認、公開可否を AI Agent またはシステムの自動処理として表す | 責任の所在を誤って示すため |
| 特定プロジェクトの実行計画・スケジュール上のフェーズ名を、前提知識なしの読者に説明なく使う | product 仕様書がプロジェクト管理の実装詳細に依存し、可読性を損なうため |
| 代表ノード数が目安（おおむね7〜9件）を超えても、プロセスグループへまとめずそのまま並べる | ノード数が増えすぎると、領域間の受け渡しを読み手が追えなくなるため |
